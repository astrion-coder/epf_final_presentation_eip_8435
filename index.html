Two node types

BranchNode

The prefix (the bits every key below shares), left and right

H(0x01 || prefix || L || R)

LeafNode

The complete key and a 32-byte value

H(0x00 || key || value)

There are no extension nodes, because the prefix keeps the tree shallow.

Keys and zones

0x00Account headers 0x01Code chunks 0x02 – 0xFEReserved for future categories 0xFFStorage
Account34 bytes
00 H(address) sub
Code34 bytes
01 H(code_hash || i) sub
Storage66 bytes
FF H(address) H(address || i) sub

i picks a group of 256 slots or code chunks, and sub picks one inside it. Keys that differ only in sub share a stem, so they sit together.

The account header

One stem per account, 00 || H(address) || sub, with 256 sub-indices.

The header holds the account’s BASIC_DATA, its CODE_HASH and its storage slots 0–63, all under that one stem.

BASIC_DATA

Version, code_size, nonce and balance at fixed offsets in one 32-byte value. Bytes 1–3 are reserved.

Slots 0–63

Live next to the account’s header. Slot 64 and up go to the storage zone.

Three rules that matter

  1. 01Every value is 32 bytesThere is no RLP list to append a field to
  2. 02Writing zero deletesZero means absent, so a cleared slot leaves no leaf
  3. 03No storage rootAccount and slot leaves are written independently

So where does last_written_block go? EIP-8188 defines it only for the MPT, as an extra RLP field.

Final deliverable

EIP-8435

Last-Written Block in PBT Leaves

Packs last_written_block write-age metadata into the account and storage leaves of the Partitioned Binary Tree.

Standards Track Core Draft, merged
eips.ethereum.org/EIPS/eip-8435

+0 bytes in the account leaf

code_size
Shrinks from 4 bytes to 3, which still holds 16,777,215, about 256× the 64 KiB limit of EIP-7954
nonce and balance
Same offsets, same widths

+0 bytes

per account, where EIP-8188 adds 5

Why 3 bytes is enough

256× headroom over the code size limit

Code size limit64 KiB
3-byte maximum~16 MiB

Both put code_size at offset 5, as 3 bytes. From EIP-7864 and EIP-7954.

+4 bytes in the storage leaf

Extra state across ~1.5 billion slots
EIP-8435~6 GB
EIP-8188~9 GB
Hashing cost is unchanged

The BLAKE3 input stays within 2 blocks, at up to 103 bytes.

State-creation gas becomes STATE_BYTES_PER_STORAGE_SET + 4 (EIP-8037).

When it changes

Writes set it
  • Balance transfers
  • Nonce bumps, including EIP-7702
  • Fee-recipient credits
  • Withdrawals (EIP-4895)
  • New accounts and slots
  • Slot value changes
Reads never do
  • SLOAD and BALANCE
  • EXTCODESIZE, EXTCODECOPY and EXTCODEHASH
  • Reading the field itself
Reverts restore it

Journaled and rolled back with its own leaf

No cascade. A storage write never touches the account leaf.

Retrieval at will

The block number travels inside the leaf

Wherever the leaf goes, its write age goes with it. State that existed before activation reads 0 until its first write.

  • Read-only

    No execution, no side index, no state change

  • Anywhere

    Hot DB, cold blob, snapshot or block witness

  • Verifiable

    The leaf hash covers it, so an inclusion proof proves it
